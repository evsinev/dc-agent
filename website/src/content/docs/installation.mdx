## Requirements

- **JDK 21** to build and run the jar — or no JVM at all with the [native binary](#native-binary).
- On deploy targets, [daemontools](https://cr.yp.to/daemontools.html) (`svc`, `svstat`) if you
  use the `war`/`jar`/`node`/`docker` service commands.

## Build

dc-agent is a Maven multi-module project built with the bundled wrapper (`./mvnw`). A plain
build produces thin jars; the runnable agent jar comes from the `agent-shaded` profile:

```bash title="Build the agent"
./mvnw package -Pagent-shaded
# -> dc-agent-app/target/dc-agent.jar
```

## Run

The agent is configured entirely through environment variables (defaults in parentheses):

```bash title="Start the agent"
WEB_SERVER_PORT=8051 \
java -jar dc-agent-app/target/dc-agent.jar
```

The command configs are always read from `/opt/dc-agent/config` (see
[Configuration](/dc-agent/configuration/)); there is no variable for it.

| Variable | Default | Purpose |
| --- | --- | --- |
| `WEB_SERVER_PORT` | `8051` | TCP port the agent listens on |
| `WEB_SERVER_CONTEXT` | `/dc-agent` | Context path prefix for every endpoint |
| `WEB_SERVER_IDLE_TIMEOUT` | `10m` | How long a connection may stay silent (Jetty's own default is 30 s). A [zip-archive-version](/dc-agent/commands/zip-archive-version/) call waits silently for up to one minute plus its `waitTimeout`; its config is refused unless that fits. A proxy in front needs the same read timeout |
| `COMMAND_DIRS` | `/opt,/srv` | Where commands may write: a command's `dir` and the directory of a jar/war must lie inside one of these (commas and/or spaces between them). See [Configuration](/dc-agent/configuration/#where-a-command-may-write) |
| `OPT_DIR` | `./opt` | Working directory for the agent |
| `TEMP_DIR` | `/tmp` | Scratch directory for uploads; its path must be owned by root (a sticky `/tmp` is fine), see [Security](/dc-agent/internals/security/) |
| `DOCKER_DELETE_TEMP_DIR` | `true` | Delete the `docker-<name>-…` work directory under `TEMP_DIR` after each `docker push` / `docker check`; set `false` only to inspect the extracted task while debugging |
| `CONTAINER_RUNTIME` | `podman` | What `docker` in the run scripts really is: `podman` (the podman-docker wrapper) or `docker`. Only affects `securityContext.passwdEntry`; the agent checks it against `docker --version`. Set `docker` on hosts with real Docker |
| `SERVICES_DEFINITION_DIR` | `/etc/service.d` | Where Docker service definitions are written |
| `SERVICES_DIR` | `/service` | daemontools service root |
| `SERVICES_LOG_DIR` | `/var/log` | daemontools log root |
| `DAEMONTOOLS_SVC_PATH` | `/usr/bin/svc` | Path to the `svc` binary |
| `DAEMONTOOLS_SVSTAT_PATH` | `/usr/bin/svstat` | Path to the `svstat` binary |
| `UI_ADMIN_ENABLED` | `false` | Enables the `/ui/api/*` admin endpoints |
| `CONTROL_PLANE_ENABLED` | `false` | Enables the `/control-plane/api/*` endpoints |
| `CONTROL_PLANE_TOKEN` | `REPLACE_THIS_TEST_CONTROL_PLANE_TOKEN` | Bearer token for the control-plane channel. **Required** with `CONTROL_PLANE_ENABLED=true`: the agent refuses to start when it is empty or the default |
| `APP_INSTANCE_NAME` | `dc-agent` | Instance name reported by [`/app-status`](/dc-agent/reference/http-api/#app-status) |
| `APP_STATUS_TOKEN` | *(built-in random)* | Bearer token guarding [`/app-status`](/dc-agent/reference/http-api/#app-status); set your own in production |

:::note
Every endpoint is served under the context path, e.g. `http://host:8051/dc-agent/health`.
The tables and examples throughout these docs assume the default context `/dc-agent`.
:::

## Supervise under daemontools

In production the agent itself is typically run as a daemontools service. A minimal `run`
script:

```bash title="/service/dc-agent/run"
#!/bin/sh
exec 2>&1
cd /opt/dc-agent || exit 1
export WEB_SERVER_PORT=8051
exec java -jar /opt/dc-agent/dc-agent.jar
```

Check status and control it with `svstat /service/dc-agent` and `svc -d`/`svc -u /service/dc-agent`.

## Native binary

Each release also carries the agent as a native executable, `dc-agent-<version>-linux-x86_64`:
no JVM on the host, about 50 MB of memory at start instead of about 250 MB, the same commands,
variables, configs and HTTP API. It is built with [Mandrel](https://github.com/graalvm/mandrel)
(GraalVM native-image) and runs on **x86_64 Linux with glibc 2.34 or newer** — EL9 (AlmaLinux,
Rocky, RHEL 9), Ubuntu 22.04+, Debian 12+ — on any x86_64 CPU.

```bash title="Install"
cd /opt/dc-agent
curl -fLO https://github.com/evsinev/dc-agent/releases/download/1.10.0/dc-agent-1.10.0-linux-x86_64
curl -fLO https://github.com/evsinev/dc-agent/releases/download/1.10.0/dc-agent-1.10.0-linux-x86_64.sha256
sha256sum -c dc-agent-1.10.0-linux-x86_64.sha256
install -m 0755 dc-agent-1.10.0-linux-x86_64 /opt/dc-agent/dc-agent
```

```bash title="/service/dc-agent/run"
#!/bin/sh
exec 2>&1
cd /opt/dc-agent || exit 1
export WEB_SERVER_PORT=8051
exec /opt/dc-agent/dc-agent
```

- The subcommands are the same: `dc-agent check-config`, `printf '%s\n' "$SECRET" | dc-agent hash-key`.
- **Memory:** the heap is capped at 256 MB, like the jar's usual `-Xmx256m`; `-Xmx` on the command
  line still changes it (`exec /opt/dc-agent/dc-agent -Xmx512m`). One garbage collector (Serial).
- **TLS:** the binary trusts the **host's** CA certificates (`/etc/pki/java/cacerts`, kept by
  `update-ca-trust` on EL; `/etc/ssl/certs/java/cacerts` on Debian/Ubuntu), not the ones it was
  built with — a corporate CA added to the host works. `-Djavax.net.ssl.trustStore=…` overrides it.
  With none of these files readable, the CAs built into the binary are used (a warning in the log).
- The release also lists what the binary was built from (`….inputs.txt`: the jar's and every
  dependency's sha256, the builder image).

To build it yourself (needs podman or docker):

```bash title="Build the native agent"
./mvnw package -Pagent-shaded -pl dc-agent-app -am
native/build.sh dc-agent-app/target/dc-agent.jar dc-agent       # in the pinned Mandrel image
native/smoke/run.sh native dc-agent                              # the release smoke, in a container
```

## Reverse proxy / TLS

The agent speaks plain HTTP. Terminate TLS in front of it (nginx, HAProxy, …) and forward the
`/dc-agent/` path through unchanged:

```nginx title="nginx"
server {
    listen 443 ssl;
    server_name dc-agent.example.com;
    # ssl_certificate / ssl_certificate_key ...

    location /dc-agent/ {
        proxy_pass http://127.0.0.1:8051;
        proxy_set_header Host $host;
        client_max_body_size 512m;   # uploads can be large
    }
}
```

## Minimal working config

Create one config file per command in `/opt/dc-agent/config`. Make a secret for the caller and
hash it — the config stores only the hash:

```bash
SECRET=$(openssl rand -hex 32)          # give this to the CI, e.g. as a masked variable
printf '%s\n' "$SECRET" | java -jar /opt/dc-agent/dc-agent.jar hash-key
```

For a `save-artifact` endpoint named `sbp-android`, create `config/sbp-android.json` with the
printed `sha256:…`:


Then upload:

```bash
curl --fail \
  --data-binary @app-release.apk \
  -H "api-key: $SECRET" \
  https://dc-agent.example.com/dc-agent/save-artifact/sbp-android/1.0.0
```

See [Configuration](/dc-agent/configuration/) for the config file format and the api-key model.

## Upgrading to 1.9

1.9 checks the configs strictly and hashes the api keys at start; an agent with a config it does
not accept **does not start**. Before replacing the jar on a host:

1. Run the check with the **new** jar — it writes nothing:

   ```bash
   java -jar dc-agent-1.9.jar check-config
   ```

2. Fix what it lists: add `"type"` to every config, move `dir` / `jarFilename` / `warFilename`
   inside `COMMAND_DIRS`, make sure the configs live in `/opt/dc-agent/config` and remove
   `CONFIG_DIR` from the agent's run script.

   A jar (war, node bundle) kept in `/service/<name>/` moves with its service: create the new
   directory (say `/opt/<name>/`; the agent does not create it), copy the current file there,
   change the service's own `run` script (and its working directory) to start it from there,
   restart the service, and only then change `jarFilename`. The agent never edits a `run`
   script, and a deploy stops the service before it writes the new file.
3. Replace the jar and restart. The first start hashes the plaintext keys (the log names each
   rewritten file) — the callers keep their secrets, nothing changes for them.

There is no way back to 1.8 without the plaintext keys: keep the CI's copy, or a backup of
`/opt/dc-agent/config` taken before the upgrade, somewhere only you can read.
